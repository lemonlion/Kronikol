# REPORT_FORMAT_PLAN harness

The scripts behind [`REPORT_FORMAT_PLAN.md`](../REPORT_FORMAT_PLAN.md) sections 2 and 3. Each one prints sizes,
counts and timings only, never report content, so its output is safe to read in an agent session. Their output from
2026-10-18 is in [`results/`](results/).

The inputs were BreakfastProvider's reports as its Pages site served them on 2026-10-18, written by Kronikol 4.9.1
(`kronikolVersion` in each file):

- `reports/lightbdd/TestRunReport.json`, 6,150,370 bytes
- `reports/reqnroll/TestRunReport.json`, 5,762,341 bytes
- `reports/docker/lightbdd/TestRunReport.json`, 5,665,856 bytes
- `reports/lightbdd/TestRunReport.html`, 3,265,019 bytes (for `html_steps.py`)

All three are under `https://lemonlion.github.io/BreakfastProvider/`. Download each with `Accept-Encoding: identity`, so
the bytes on disk are the bytes Kronikol wrote.

| File | What it prints |
|---|---|
| `measure.py` | The file's whitespace outside strings. Its bytes by part: steps (with the bytes spent on keys written as `null` or `[]`), call metadata, bodies, and diagrams, stored and decoded. The step depth histogram. Then six forms of the same data (as written, compact, compact without nulls, every `$z` decoded with and without indentation, decoded without nulls), each under gzip 6, zstd 3, zstd 19, brotli 9 (24-bit window) and xz 6, with gzip's inflate time |
| `codecs.py` | The content a `.krkl` would hold (every `$z` decoded, compact, no nulls) under each codec and level, with write and read times, through Python's native bindings |
| `marker.py` | Kronikol's marker (a zstd skippable frame) in front of a level 9 frame with its checksum: whether Python's one-shot `compression.zstd.decompress` and its streaming `ZstdDecompressor` return the content, the frame's recorded content size, and whether a corrupted and a truncated file are detected. Writes the marked file for `marker.cs` |
| `marker.cs` | The same through ZstdSharp 0.8.8 (`Unwrap` and `DecompressionStream`, over the marker and after it), the exception types for a corrupted and a truncated file, and whether a streamed frame records its content size |
| `scale.py`, `scale.cs` | The 150 MB synthetic report of `tools/query-bench` (gitignored, generated by `tools/query-bench/gen`) as `.krkl` content: gzip, zstd 3, zstd 9 and zstd 9 with long-distance matching in Python, and ZstdSharp against .NET's gzip. The corpus is extremely repetitive, so its ratios mean nothing; it shows that 115 MB writes and decodes in well under a second |
| `content.py` | Writes that content to a file, for `codecs.cs` |
| `codecs.cs` | The same content in .NET 10: gzip (`Optimal`, `SmallestSize`), zstd 3, 9, 12 and 19 through ZstdSharp.Port, brotli 5 and 9 (built in, 24-bit window). Run `dotnet run codecs.cs -- <content file>` from a folder outside the repository, so the repository's central package management does not apply to it |
| `deepmodel.py` | One LightBDD composite step with three text segments, as the full step mapper writes it, measured at depths 0 to 20 indented (CRLF, as a Windows run writes the file), compact, and compact without nulls. The figure for 210 steps in ten chains 20 deep. Synthetic: its gzip figures are not representative, since every step is nearly the same |
| `blocked.py` | One gzip stream against one gzip member per scenario (a multi-member gzip file of the same bytes, which any gzip reader decodes as one stream) |
| `html_steps.py` | What a `TestRunReport.html` spends on steps: step elements, their markup up to `</summary>` or `</div>`, the status tooltips (their text, and the whole `title` attributes) and how many are distinct, and the collapsible composites (open and closed). Run it on the deep-steps consumer's page for A1 |
| `brotli_levels.py` | Brotli qualities 4 to 7 with 22- and 24-bit windows on the `.krkl` content: size, write and read time |
| `notes.py` | #120 inside one compressed stream: each diagram note of 200 or more characters replaced by a short reference, under gzip 6, zstd 9, zstd 19 and brotli 5. Then the per-payload `$z` threshold inside the container (8,192, 65,536, 262,144 and off): the decoded working set the tool would hold, and the zstd 9 and brotli 5 sizes |
| `payload_split.py` | What the `$z` payloads cost under `zstd -3` of the file as written (the `zstd` command's default) against what they cost inside a `.krkl`, and what everything else costs at each: how a report compressed with `zstd` compares with its `.krkl` |

```bash
PYTHONUTF8=1 python -E measure.py <TestRunReport.json>...
PYTHONUTF8=1 python -E codecs.py <TestRunReport.json>
PYTHONUTF8=1 python -E deepmodel.py
PYTHONUTF8=1 python -E blocked.py <TestRunReport.json>...
PYTHONUTF8=1 python -E notes.py <TestRunReport.json>...
PYTHONUTF8=1 python -E payload_split.py <TestRunReport.json>
PYTHONUTF8=1 python -E html_steps.py <TestRunReport.html>
PYTHONUTF8=1 python -E brotli_levels.py content.bin
PYTHONUTF8=1 python -E content.py <TestRunReport.json> content.bin
dotnet run codecs.cs -- content.bin
PYTHONUTF8=1 python -E marker.py content.bin marked.krkl
dotnet run marker.cs -- content.bin marked.krkl
PYTHONUTF8=1 python -E scale.py <query-bench report> scale-content.bin
dotnet run scale.cs -- scale-content.bin
```

The Python scripts need Python 3.14 or later (`compression.zstd` is in the standard library from 3.14) and the
`brotli` package. `-E` rather than `-I`, because `-I` hides the user site-packages that hold `brotli`. Run them from
a folder that holds no downloaded files. The machine was Windows 11 with Python 3.14.4 and .NET 10.0.11. Timings move
by about 20% between runs; the sizes do not move.
