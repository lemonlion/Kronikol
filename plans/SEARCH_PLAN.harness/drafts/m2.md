# M2: `tag:`, `status:` and `feature:` in real search text (SEARCH_PLAN 4.4, S3)

Measured 2026-10-26, before the forms were added, by `m2-count.js` beside this file (`node m2-count.js`). It reads the
text the instant search matches, every `data-search` and `data-row-search` attribute, of every report below, and counts
a key followed by a letter or digit: standing on its own (at the start, after a space, bracket, quote or other
punctuation, with or without a `-`) and, apart, inside a word (`hashtag:x`, `httpstatus:200`), which is never read as a
form. It prints numbers and shapes only, never the text. A compressed page, whose file holds no `data-search`, is opened
in the bundled Chromium and read once it has decoded itself. Files are counted once by their bytes (62 E2E fixtures were
byte for byte one already read, in another worktree).

`dep:`, `dependency:`, `duration:` and `is:` are counted beside the three new keys, as the measure 5.0.0 took for its
qualifiers (D16, measured at 0).

|---|---|---|---|---|---|---|---|
| BreakfastProvider, .NET ReqNRoll lane (Kronikol 4.26.4; its Specifications page has no search text) | 2 | 230 | 0 | 0 | 0 | 0 | 0 |

| **All** | **1,849** | **16,741** | **0** | **0** | **0** | **0** | **0** |

No source holds any of the keys followed by a letter or digit, on its own or inside a word, so no clash was found:
no text a reader could have searched for before reads differently now. A planted text (`status:400`, `tag:smoke`,
`(feature:a)`, `-status:failed`, `httpstatus:200`, `dep:pay`) is counted as it should be, so the zeros are zeros of
the text and not of the counter.

Not measured: the live BreakfastProvider demo (the 214-scenario report section 2.1 measured), as the measure reads
reports on disk; the on-disk .NET lane is the same project's suite at 4.26.4.
