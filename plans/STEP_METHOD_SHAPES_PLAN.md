**Written:** 2026-11-02, at 5.27.13 (`v5.27.13`, `c58d98c0`; main at `27cc0e46`), at the owner's ask to plan a fix for the
underlying problem, which may differ from the one the issue proposes. **Status: executed. Green-lit by the owner on 2026-11-04 ("implement the plan in full"), every question taken at its recommendation: Q9's patch shipped as 5.28.3, the rest as 5.29.0, and #226 is closed.** The fix was built first to test the design, and where this plan says "the prototype" it means that build. Its patch stood beside this file until the release, and git history has it (`plans/STEP_METHOD_SHAPES_PLAN.prototype.patch` at `7a8b98a3`). The results named for the prototype were measured again on the code as released, so the names stay and the numbers are the release's.

**Re-checked:** 2026-11-03, at 5.28.2 (`v5.28.2`, `cc8f459a`; main at `9d994a4b`), at the owner's ask to make sure it is complete and accurate and to do any deep dive that might change it. Section 13 says what that changed. Neither weaver, `StepCollector.cs` nor their tests moved between the two commits, so the `file:line` citations hold at both.

Evidence labels: **RUN** (measured here, against the published 5.28.2 packages or the weaver at `9d994a4b`, unless the line says otherwise), **READ** (in the source, `file:line` at `9d994a4b`), **DOC** (a vendor's own documentation or source, fetched 2026-11-02 or 2026-11-03), **INFERRED** (reasoned from facts, stated by none), **ISSUE** (taken from the issue, not re-measured). Every RUN line

A family's letter and two or three digits, such as A00, F01 and Z105, name rows of that probe's shape list, and a number with lettered rows (Z01a, Z01b) stands for all of them. Family F's numbers meet the findings' from 10 up, so a shape there is always written with its name, as `F13-pointer`.

#226 reports that a `[Step]` method returning an `int` or a `ValueTask` throws `InvalidProgramException` when it is called. It
suggests storing the value in a local before each `leave`, following a `ValueTask` as a `Task` is followed, and warning at build
time about what cannot be wrapped. The report is right, and reproduces on the published packages. The suggestions are right as far
as they go, and they reach two of the places where the same mistake is made.

## 0. Summary

**The underlying problem is that the weaver has no model of the method it wraps, and nothing checks what it emits.** It holds two
wrappers, each of which assumes a shape of method. `GetAsyncKind` recognises two return types by name and calls everything else
`None`, and `None` means a `void` method (`StepWeaver.cs:156-161`, `:357-365`). The same assumption is repeated at twelve sites (section 2): the success path, the bypass path, the default a bypass returns, the capture of each parameter, the member `SkipIf` names. A method
none of them assumed is not refused. It is given IL that is wrong for it, and the first anything knows is the JIT at the first call.

The issue's symptom is the mildest of what follows from that. A shape probe ran 635 method shapes through the weaver in Debug
and Release, IL-verified each, JIT-compiled each and ran each:

| | Runs that do what they should |
|---|---|
| The weaver on main (`9d994a4b`) | **316** of 1270 |
| Main with F29's patch alone (5.28.3) | **334** of 1270 |
| The code as released, its list grown by 13 shapes in execution | **1296** of 1296 |
| The same with the JIT at full optimisation | **1296** of 1296 |
| The same on the .NET 11 runtime (RC3) | **1296** of 1296 |
| The weaver on main, on Linux | **314** of 1270 |
| The code as released, on Linux | **1294** of 1296, the two misses being one shape in each configuration, which Linux cannot run at all (`__arglist`) |

Compiled in Release with `/debug+`, which xUnit v2 turns on and the two configurations above do not, main gets 153 of 635 and the code as released 648 of 648.

A second run asks another question, whether the weave changes what a program does. It holds one body twice, with an assertion and with a plain identity in its place, for 15 conditions in 31 kinds of statement, in a plain method under a step and as a value step, and only the first is woven. Main changes the program in 1,245 of 1,860 runs: 840 are a value step's crash, and 405 give a different answer with no word, 360 of them in plain methods with no step in sight. The prototype changes it in none (RUN, `results/differential-*.txt`).

What main does to the rest, worst first (section 4):

- **Outside the step weaver, and worse than anything below: an assertion's result used in a condition takes the wrong way in Release, with no word** (F29). `if (s.ShouldNotBeNull().Length > 5)` runs the then-part whatever the length, and `while (true) { if (...) break; }` never ends. A test can pass or fail for the wrong reason. It is not the step weaver's, and it can ship ahead of all this (Q9).

- **A `ref`, `in` or `out` parameter kills the test process.** The weaver stores the managed pointer in an `object[]`, and the
  collector reads it as an object. Under the xUnit adapter, three facts with one such step in the second: *"Catastrophic failure: Test
  process crashed with exit code -1073741819"*, and no result for any of the three (F1). The issue does not mention parameters.
- **A `Task` method that throws before it has a task loses its step.** A guard clause is enough. The step stays open for the rest of the
  scenario, later steps nest under it, and it never reaches the report, so a failed step is not there to read (F3).
- **A bypassed sub-step also closes its parent,** on the shapes that are supported today (`void` and `Task`), because the bypass's own
  `ret` is rewritten along with the method's (F4).
- **`SkipIf` on a `Task<Guid>`, a `Task<decimal>` or any such struct throws `InvalidProgramException` at every call, skipped or not** (F6).
- **`DebugType=embedded` or `none` silently weaves nothing:** every `[Step]` in the project is gone from the report, with no warning (F11).
- **Not the step weaver's, and in the same patch: an assertion that opens a `finally` or a `catch` throws `InvalidProgramException` in Release** (F23).

**The fix is one wrapper over one decision** (section 7): classify each method once, in a function that names every outcome; emit one
bracket for all of them, where the only thing that varies is how the method's end reads; leave what no bracket can tell the truth about as
the compiler wrote it, and say so in the build. Then pin it where it has never been pinned: every shape IL-verified before it is run. The prototype shows one wrapper is enough: it replaces both. `StepWeaver.cs` goes from 912 lines to 1,421, since the classification, the refusal and the walk for `SkipIf`'s member are new (section 8).

It is **one minor release** (two new warning codes and new members on `WeaveResult`), with no new runtime member, so a new weaver works over
an older core, which the package's lack of a declared dependency allows (RUN). Section 10 has eight decisions for the owner, each with a recommendation.

An independent review of this plan and its first prototype found what the first shape list missed, among them a build break the prototype itself introduced, in the issue's own shape (F19). Its shapes are family Z, and the prototype here has its fixes (section 13). A second one, given the code and the re-checked prototype and no conclusions, found six things main does and that prototype did not, a false warning that would have failed builds among them. Five are fixed and one accepted, and that changed Q6's recommendation. A third, given the patch and its own questions, ran about 30,000 shapes and about 50 real builds and found four more regressions, each a correction made too broadly, and eight defects main shares. All are fixed but one, a pinned limit (Z134). A fourth, given the code and the plan with no conclusions, found the check written for the third still refusing the compiler's own null path, which cost a note and added a warning in a project with no step at all, and found that the stage table could not be followed as written. Both are fixed (section 13). A fifth, on what changed after the fourth, found the worst thing here, F29, which no list of shapes had and which the published packages do today, and two regressions in this plan's own symbol write. All are fixed.

**.NET 11 changes none of this by default:** a net11.0 project on the release candidate still gets state machines, and the same defects (RUN). Turning runtime async on takes one project property, and then every `async` step that returns a `Task` or a value throws on main. The prototype brackets those too, with one limit (F20, Q8).

## 2. How a step method is woven today

`StepWeaver.Weave` walks every method with a step attribute and calls `WrapMethodWithStepTracking` (`StepWeaver.cs:110-122`), which
asks `GetAsyncKind` and takes one of two paths (READ).

The **sync path** (`:146-352`) inserts `StartStep` before the first instruction, turns each `ret` into a `leave` to a block after a
`catch`, and ends that block in a bare `ret`. The **async path** (`:373-536`) inserts `StartStep`, wraps nothing, and puts a call to
`StepCollector.CompleteStepAsync` before each `ret`. Each holds its own copy of the parameter capture and the `SkipIf` read.

Each row below is one site that assumes a shape, and each is measured in section 4:

| Site | READ at | Assumes | Is wrong for |
|---|---|---|---|
| Sync success path | `:314`, `:319-324` | The method returns nothing | Any value (the issue) |
| Sync bypass | `:284` | The method returns nothing | `SkipIf` on any value |
| `GetAsyncKind` | `:357-365` | `Task` and `Task<T>` are the only things to wait for, and anything else is void | `ValueTask`, iterators, other awaitables (the issue, in part) |
| Order of the rewrite | `:319`, `:527` after the preamble | The only `ret`s are the method's own | Every bypass: its `ret` is rewritten too, so it completes a second time |
| Async path | `:527-532` | A task-returning method cannot throw before it returns | A guard clause in any non-`async` `Task` method |
| `EmitDefault` | `:509`, `:890-911` | A `T` is a reference or a small primitive; its comment says "In practice step methods returning Task<ValueType> are extremely rare" | `SkipIf` on `Task<T>` for most structs and any generic `T` |
| Parameter capture | `:218-228`, `:426-435` | Every parameter can be stored in an `object` | `ref`, `in`, `out`, spans, pointers |
| `SkipIf` read | `:263`, `:270`, `:265`, `:272` | There is a `this`; the member's type is not generic; the member can be reached; `this` is a class; a field exists at run time; the read cannot throw | Static steps, generic types, private base members, structs, a `const`, a getter that throws |
| Appended blocks | `:347` | The method does not end inside a handler | A method whose last block is a `catch` or `finally` it never leaves |
| `ret` rewritten in place | `:322` | Nothing precedes it that needs a `ret` | A `tail.` call, which F# writes (C# does not) |
| The catch | `:305` | Reading an exception's `Message` cannot throw | A `Message` that throws, which takes the place of what the method threw |
| `WeaveStepsTask` | `WeaveStepsTask.cs:47-52` | There is a `.pdb` file beside the assembly, and it is this build's | `DebugType=embedded` and `none`, a `PdbFile` written elsewhere, and a `.pdb` left in `obj` when `DebugType` changes |

Nothing checks any of it. `tests/Kronikol.Tests.StepTracking` runs 61 tests (RUN): every woven method in them returns `void` or is
`async Task`, `SkipIf` is tried on those two only, and no fact reads the emitted IL or asks the JIT about a method it does not call.

## 5. The underlying problem

A weaver is a compiler with no type checker. Roslyn would refuse every method in section 4, but the weaver writes IL past the point
where anything checks it. So the only things standing between a wrong assumption and a user's test run are the weaver's own logic and its
tests, and both name a closed list: `void` and `Task`.

Three things make that worse than a list that is too short.

**The default is a guess, not a refusal.** A method outside the list is not rejected; it is treated as `void`. So a new shape arrives as
wrong code, never as a message. C# has grown shapes for years (`ValueTask` in 7, ref returns in 7, `in` in 7.2, local function attributes in
9, lambda attributes in 10, `params` spans in 13) and each one landed on that default.

**The assumption is repeated, not held in one place.** The two wrappers hold copies of the same code, and each site decides for itself what the method looks like. That is why a local-and-overload fix would leave most of section 4 standing, and how F4 survived: each
wrapper's rewrite pass looks for `ret` after its own preamble has added one.

**The step weaver missed what its sibling learned.** The assertion weaver has met several of these and fixed each one, in its own file:

| Learned by the assertion weaver | Where | In the step weaver |
|---|---|---|
| A statement it cannot account for is left as written, and the build says so. Its comment says "never miscompiled", which F29 shows is the aim and not yet the fact | `WeaveAssertionsTask.cs:108-127`, #212 | Miscompiled, silently |
| A project with no `.pdb` file is woven | `AssertionWeaver.cs:83`, `:192-226` | Skipped at low importance (F11) |
| The build's references come before the current directory | `AssertionWeaver.cs:296-330` | Not (F17) |
| The sentinel is an `Attribute` with a base call | `AssertionWeaver.cs:266-294` | Not (F9) |

The fix follows from those three. There is one place that decides, what it does not recognise is said out loud, and the output is checked.

## 7. The fix

### 7.1 One decision

`ClassifyReturn` runs once per step method and names every outcome. Nothing falls through to `void`.

| In this order | Kind | The step ends |
|---|---|---|
| No body at all (Q6) | Not woven, not refused: a line at normal verbosity, and no warning | |
| Compiled for runtime async, `MethodImplAttributes.Async` (F20, Q8) | `Void` for a `Task` or a `ValueTask`, `Value` for a `Task<T>` or a `ValueTask<T>`, with `T` as the value's type. Any other return type is refused | When the method's work does |
| `[IteratorStateMachine]` or `[AsyncIteratorStateMachine]` | Refused | |
| `void`, with `[AsyncStateMachine]` | Refused, unless it has a `SkipIf`, which a refusal would ignore: then `Void`, and its step closes at its first `await` as on main (Z130, Q2) | |
| `void` | `Void` | When the method returns |
| `System.Threading.Tasks.Task`, `Task<T>` | `Task`, `GenericTask` | When the task does |
| `System.Threading.Tasks.ValueTask`, `ValueTask<T>` | `ValueTask`, `GenericValueTask` | When the task does |
| Anything else with `[AsyncStateMachine]` (a task-like), or with an instance `GetAwaiter()` that a caller could use: no parameters, no type parameters, not `void`, and public or `internal` to a friend, on it, a base or a base interface. A type parameter counts as what it is constrained to (E26, Z135) | Refused | |
| Anything else | `Value` | When the method returns |

Every test looks through modifiers first: an `init` accessor returns `void` under a `modreq`, and a virtual `ref readonly` return is a by-ref under one (G05, B04-ref-readonly-virtual).
`IsAwaitable` stops at an array, pointer, by-ref or function pointer, since Cecil resolves `Task[]` to `Task` (E25), and reads a type parameter as what it is constrained to (E26, Z135).

A lazy `IEnumerable<T>` with no `yield` is a `Value`, and so are an `object` holding a task, a `T` with no constraint that holds one, a `ref Task`, and a type awaitable only through an extension `GetAwaiter`
(E20, E22, Z109). The weaver cannot see any of them, and the step honestly ends at the call. A `GetAwaiter` no caller could use makes nothing awaitable (Z108).

**A partial method is the one known hole.** Roslyn writes no state-machine attribute on a partial method (RUN, 5.3 and 5.6) or a partial getter (5.12), so `[Step] partial IEnumerable<int> M()` is a `Value` whose step closes before its body runs, and `async partial void M()` reads as `Void`. On main the first fails at the JIT and the second reads as it does here. The attribute is the contract, since the lowering is none, and refusing every `IEnumerable` would refuse the lazy methods above, so this is pinned as a limit (Z106). The reverse holds as well: a `[AsyncStateMachine]` written by hand on a plain `void` is refused, though main drew it. No compiler writes that.

**Reading a method never fails the build.** `ClassifyReturn` and `GetSkipIfInfo` run before the method is touched, so a failure there leaves it whole. If classifying throws, the method is refused and the warning carries the exception's type and message. If the `SkipIf` read throws, `KRONIKOL005` says so and the step runs. A resolve that cannot find or open an assembly, one held open for writing among them, reads as an unknown type (Z102). The `try` in `WeaveStepsTask.Execute` (`WeaveStepsTask.cs:28-36`) stays for what is left, as on main.

The methods of a C# 14 extension block's skeleton (`<G>$...`) are not looked at: what runs is the static method the compiler writes on the enclosing class (F21).

**A method compiled for runtime async has no stub.** It is one frame to the JIT, each `await` an ordinary call in it, and its `ret` hands back the task's result. So its step takes the sync shape, with the `try` round its awaits, and ends when its work does: the value, a failure before or after an `await`, a bypass and sub-steps all read as they should, on .NET 10 with the switch and on .NET 11 (Z70-Z83). One thing cannot hold, as it comes from the stub: `StartStep` runs in the method's own frame, and the runtime undoes an `AsyncLocal` write there when the method returns. So an async `[WhenStep]` moves the phase inside itself and not for its caller, whether or not it suspends (RUN, `results/net11-prototype.txt`), and a call the test makes itself after it, outside any step, keeps the phase it had. And #225's rule that a caller has moved on, which it sets in `CompleteStepAsync`, is not reached (section 11). Q8 has the choice.

### 7.2 One wrapper

```
StartStep(keyword, text, names, values)
try {
    [SkipIf: read the member; if false, on to the body; BypassStep(reason); default each out parameter; leave bypassed]
    the method's body, each ret becoming:   stloc result; leave end     (or leave end, for void)
                                            stloc result; ldloca result; AsTask; stloc task; leave end     (a ValueTask)
}
catch (Exception) {
    try { message = ex.Message } catch { }
    CompleteStep(false, message); rethrow
}
end:
    Void, Value:        CompleteStep(true, null); [ldloc result]; ret
    Task, Task<T>:      ldloc result; CompleteStepAsync; ret
    ValueTask, <T>:     ldloc task; CompleteStepAsync; newobj ValueTask(Task); ret
bypassed:
    as the method would leave, 7.3; ret
```

- **The bypass has its own way out, past the end,** so nothing in it reaches `CompleteStep` (F4), and its read sits inside the `try`, so a getter that throws fails the step and leaves it closed (Z02).
- **A `ret` is changed in place,** as the sync path learned from an earlier `InvalidProgramException` (`d0e324b1`), so a branch to it still lands there, with the value on the
  stack. A `leave` empties the stack and `ret` needs exactly the return value on it, which is why the value travels in a local (DOC).
- **Every kind gets the `try`.** A non-`async` method throwing before it has a task reaches the catch (F3). An `async` method never does, its state machine putting what it throws in its task, so the catch is dead code there. Keeping it means one path to test. Under runtime async there is no state machine, and the catch is what fails the step (Z78, Z79).
- **The end sits outside the `try`,** so a step that passed cannot also fail. Nothing in that block throws today, so no shape pins the order. `AsTask` runs inside the `try`, because it can throw: it reads a source's `GetStatus`, and a source that throws there is the method's failure, with its step closed (Z113).
- **Reading `Message` runs the exception's own code,** so it has a `try` of its own. If it throws, the step fails with no message and the caller still gets what the method threw (F22).
- **A handler the method ended in gets a real end** before anything is appended (F8), and a `tail.` prefix becomes a `nop` (F15).
- **What is appended sits behind a hidden sequence point,** which ends the method's last statement where the source does (F18). A debugger does not step into it either.
- **`CompleteStepAsync` runs in the stub's frame, synchronously.** Nothing awaits or defers between the body and that call. #225's R1 relies on this: it makes the method plain so that
  the caller's flow moves back to the parent there. Keep it.

### 7.3 The bypass leaves as the method would

| Kind | The bypass returns |
|---|---|
| `Void` | Nothing |
| `Value`, `ValueTask`, `ValueTask<T>` | The `result` local, which `InitLocals` has left as the type's default. A default `ValueTask` is a completed one (DOC) |
| `Task` | `Task.CompletedTask` |
| `Task<T>` | `Task.FromResult<T>(a local never written to)`, which is right for every `T` and removes `EmitDefault` |
| A `ref` return | There is no default reference to hand back, so `SkipIf` is dropped with a warning, and the step runs (H08), as it does for a member it cannot use |

Under runtime async the kinds are `Void` and `Value`, with the task's result as the value, so a bypass returns nothing or the result's default and the runtime wraps it (Z80, Z82).

Each `out` parameter is set to its default first (H09), since a caller may rely on it being assigned. `InitLocals` is set on every woven method, or a `[SkipLocalsInit]` method's bypass would hand back whatever was on the stack (H13).

### 7.5 `SkipIf`'s member

- Every reference names a closed type, read through the step's own view: `Steps<T>` for itself, and a base's arguments as the derived type gives them, through any depth, pointers and arrays among them (H26, H37, H38, Z44).
- The member is the one C# bound. The walk goes on past a member the step's type cannot see to the one it can (Z04). A private member reaches a type nested in its owner (Z03a, Z03b), and an `internal` one a friend, through `InternalsVisibleTo` (Z03c).
- A friend's name is compared without regard to case, as the runtime compares it, and `IgnoresAccessChecksTo` on the step's assembly reaches anything (Z103, Z104). A base whose arguments hold a function pointer is closed like any other (Z101).
- A `const` is its value, since it has no field at run time (Z01). A `volatile` field is read as what it is, under its modifier, in a generic base too (Z110).
- An instance member on a static step (H24), a member a derived type cannot reach (H27), an indexer (H36), a static abstract member (Z05b) and a `ref` return (H08): a warning, and the step runs, which is what a missing member gets today (Q7).
- A static virtual member with a body reads that body, as on main, and with no word, whatever a type overrides it with (Z05a, Z111). A method on the interface has no type argument to read an override through, and C# has no such read either (RUN: `CS8926`).
- A struct's getter is `call`, since its `this` is a reference (H29).
- A lambda or a local function converted to a delegate lives on a type the compiler made, so its member is not found: it warns and runs, as on main.

### 7.6 What no bracket can tell the truth about

A refused method is **left as the compiler wrote it**: no `StartStep`, no bracket, and it runs normally. `WeaveResult.UnwovenSteps` lists it, and the task warns once, as `KRONIKOL003` does:

```
warning KRONIKOL004: Kronikol.StepTracking: 2 step method(s) were left as written, so they run without a step. First: Program.cs, line 77, in ShopDriver.An_iterator: it is an iterator, whose body runs
while its caller enumerates it, after the method has returned. The build lists each one at normal verbosity (-v:n).
```

`<NoWarn>KRONIKOL004</NoWarn>` silences it. The `SkipIf` warnings, which have no code today so nothing can silence them, take `KRONIKOL005`.

A method with no body is not in that list, since nothing about it is wrong: what runs is an override, which takes a step attribute of its own or does not, or for an `extern` the native code, which the weaver cannot reach. `WeaveResult.StepsWithNoBody` holds it, and `-v:n` prints a line (Q6).

This is the assertion weaver's rule, and its comment says it best: "A statement the weave cannot account for is left as the compiler wrote it, never miscompiled" (`WeaveAssertionsTask.cs:108`). It is the rule and not yet the fact: a statement whose own branch goes elsewhere is accounted for wrongly on main, and takes the wrong way with no word (F29).

### 7.7 What the assertion weaver already learned

Ported as they stand: `Weave(string, string?)` weaves with no `.pdb` file, writing embedded symbols back and none where there were none (F11); the resolver's search order (F17); the sentinel (F9). New in both, since neither had them: the resolver is disposed (F19), and the project's `PdbFile` reaches each task, so symbols written elsewhere are read and written back, not lost (RUN: steps and notes drawn and line numbers kept, where main weaves no step and says of its notes that the build writes no PDB, `results/consumer-*.txt`). Its extension is changed to `.pdb` as the build does (RUN: a `PdbFile` with none and with another, `results/real-build-settings.txt`). A `PdbFile` not named after the assembly is written by Cecil to a file it opens itself, since Cecil names the PDB after the assembly for any stream and the runtime finds it by the name in the assembly (F28). Cecil takes that file's path from the assembly's, so the assembly is written beside it under an extension of the weave's own and copied over the real one, and a file of the project's that bears the PDB's name is not touched (Z136c). Cecil records the file's full path, which would carry a folder of this machine into a build with mapped paths and make two clones differ, so the weave blanks the record down to the file's name, which is what the assembly names on the other path too: two clones under a path map come out byte for byte the same, with their line numbers (RUN, `results/real-build-settings.txt`, Z136). The compare with the assembly's name goes by case, or `AssemblyName=App` with `PdbFile=symbols/app.pdb` loses its line numbers on Linux (RUN, `results/linux-consumers.txt`, Z136d). A stale `.pdb` is left alone where the assembly embeds its symbols (F24). A local function reads by its own name, a lambda by its method's, a lambda in a field's initializer by its type's as written, and an explicit implementation by the name after its interface's (F14). In both weavers a `.pdb` that is not this assembly's, which `SymbolsNotMatchingException` says, is passed over and the weave goes on with what the assembly embeds, so a `DebugType` edit does not need a clean (F24). With nothing embedded the step weaver needs nothing more, and the assertion weaver has no statements to find, which `KRONIKOL001` already says.

**The assertion weaver's own edits,** none of them a port. An assertion that opens a handler moves that handler's `TryEnd` and `HandlerStart` as well, and the handler before it ends where that begins, so its wrapper starts inside it (F23). What follows is read past any `nop`, `br` or `leave`, and two returns in a method are the same way on, so a null path in a `then` arm keeps its note (Z143b). A reference at version 0.0.0.0 is read through to the core's own (F25). A statement in a value-returning step is refused when it holds a `leave` to the end of the step's wrapper: in a real build the step weaver runs first, a `ret` is a `leave` by the time the assertion weaver looks, and its check for a statement that returns part-way looked only for `ret`, so `[Step] bool M(string s) => s.ShouldNotBeNull() != null && s.Length > 0;` would run the assertion and lose its note with nothing said (Z124; on main the step throws first, so nothing shows it). The wrapper is known by its catch, the handler that calls `StepCollector`, so no attribute's name is read. Any other `leave` is the compiler's own, out of a `using`, a `lock` or a `try`, and the method carries on after it: `s?.ShouldBe("a");` there has no assertion to lose on its null path (Z128, which the third review found the first cut refusing), and `s.ShouldNotBeNull()?.ShouldBe("a");` there keeps its note on the path that runs (Z137, which the fourth review found the second cut refusing, in a project with no step at all).  An `init` accessor is read as the `void` it is, under its modreq (Z138). A ternary with an assertion in each arm passed before this check only because its driver took the arm that keeps its note: Z35b takes the other. And `StackAnalysis` reads a runtime-async `ret` by what it carries, which a `Task`'s does not (Z83). The package declares no dependency, so a project can hold a new step weaver over an older assertion weaver, and it then gets what the older one does on these shapes: the note lost on the short-circuit, `KRONIKOL003` under runtime async, and the stale PDB's failure (RUN: `results/consumer-prototype-over-published-assertions.txt`, `results/real-build-settings.txt`, and the review). ## 10. Questions for the owner

Decisions only. Each has a recommendation, and the prototype follows it unless the question says otherwise. **The owner took Q1 to Q9 at their recommendations on 2026-11-04, by asking for the plan in full.** Q10 came up in execution and is open.

- **Q10. A getter named in an assertion runs again for the note.** `1.ShouldBe(c.Next)` with `public int Next => ++N;` leaves `N` at 2 where the program alone leaves it at 1, and a getter that dequeues or blocks does what it does a second time (the sixth review's V01, V04, E09, on main too). The note reads the value by reflection after the assertion. Reading only fields and auto-properties would end it, and a computed property's value would leave every label that shows one today, which is most of what the feature is for. **Recommend asking which matters more: not changed here.**

- **Q1. A method no bracket can tell the truth about (iterators, other awaitables): (a) left as written, with `KRONIKOL004`, or (b) wrapped, with the same warning, drawing a step that ends when the method returns?** With (b) the report shows `M: Passed, 0 ms`, and its calls land outside it. **Recommend (a):** no picture rather than a wrong one, and the same rule as `KRONIKOL003`. A refused method's `SkipIf` is not read, so its body runs whatever that says, and the warning says so, with a count, since it names only the first method in full (H35, `results/skipif-count-prototype.txt`). On main such a method throws at the call, so nothing relies on it.
- **Q2. `async void` runs today, and the fix changes it.** Today it draws a step that closes at its first `await` and always reads as passed. **Recommend the same as Q1,** so it stops being drawn and the build says why. It can break a build under `TreatWarningsAsErrors` until `NoWarn` is set. One with a `SkipIf` stays woven as any `void` method is and keeps today's reading, since a refusal would run a body the attribute says does not run (Z130; the third review found this). A `SkipIf` that names nothing usable stays woven the same way, as on main.
- **Q3. One minor, or a patch and then a minor?** The crash fixes could ship as a patch with refusal to follow, but until the second release an iterator either still fails or is unwoven with no word. **Recommend one minor.** F23 stands apart: it is a crash on the published packages for any project with assertion tracking, with no step in sight, and its fix is three edits that depend on nothing else here: `TryEnd`, `HandlerStart`, and the `HandlerEnd` of the handler before (RUN by the fourth review: the first two alone leave a second catch crashing), with F26's refusal of a statement that ends by throwing for Z133 (RUN by the fifth: the three alone leave it crashing in Release). So if this plan is to wait, ship F23 first as a patch of its own, with Z120, Z131, Z133 and Z139.
- **Q4. `KRONIKOL005` on the existing `SkipIf` warnings?** It lets a project silence them, and a `WarningsAsErrors` list by code can now name them. **Recommend yes.**
- **Q5. Record what a step returns?** The issue calls `[Step] public Customer A_customer_is_registered(…)` a natural shape, and a report could show the customer. It is a new feature with its own size questions. **Recommend not here:** this plan makes the shape run. Say if you want an issue for it.
- **Q6. A `[Step]` on a method with no body (`abstract`, an interface's, `extern`) does nothing today, and says nothing (G19). Warn under `KRONIKOL004`, or list it at normal verbosity and no more?** A warning names code that runs correctly, and it would be false wherever an override carries the attribute itself: a build with `-warnaserror` that passes today would fail, which is what the second review saw (Z100). **Recommend no warning,** with a line at `-v:n`, as the prototype does. An author who expects the override to inherit the attribute gets no word in a default build, which is how it is today.
- **Q7. A `SkipIf` the weave cannot use: run the body with a warning, or fail the step?** Today a missing member warns and runs, and a member it cannot reach throws at run time. Running a body someone meant to skip can do real work, where failing stops a suite for a reason a build could have said. **Recommend run with `KRONIKOL005`,** which is what the wiki documents for a missing member (`Step-Tracking.md:596`), and a project that wants it to fail can list the code in `WarningsAsErrors`.
- **Q8. Runtime async: (a) bracket it as 7.1 has it, with its limit stated, or (b) refuse it with `KRONIKOL004`?** Either way it stops throwing. A refused method runs, draws no step and moves no phase. A bracketed one draws its step, its failure, its bypass and its sub-steps, and moves the phase inside itself. What it cannot do from inside its own frame is move the phase for its caller (RUN), and at the top level #225's rule reads as today's tree (RUN by that plan's session). **Recommend (a):** it gets right everything a refusal gets wrong, and costs one branch in `ClassifyReturn` and two lines in the wrapper. Keeping every behaviour would take a stub with the body moved beside it, which is 6.3's second row: more code and one more frame, for a preview feature, not built here. It earns an issue if an SDK turns the feature on by default. #224 had a cut that removed the phase half of this limit, by reading the phase from the test's state, and dropped that read for what it cost elsewhere, so its current cut has the same limit on this patch (RUN by that plan's session, its F22, `STEP_PHASE_PLAN.harness/results/net11-on226.txt`).
