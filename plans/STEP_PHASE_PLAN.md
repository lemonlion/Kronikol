**Written:** 2026-11-02, at 5.27.13. **Redesigned and re-measured:** 2026-11-03, at 5.28.2 (`v5.28.2`, main at `9d994a4b`). **Status: executed, on the owner's word of 2026-11-04 ("can you implement the plan in full"), every question as recommended, with Q14's three faults named to the owner and not filed.**
R1 is 5.30.3, and it closes #195 and #224. R2 is 5.31.0. R3's code shipped in 5.29.3, with #223's R1. The sections below stand as they were reviewed, each with an **As executed** note where a release differs, and the last entry of §12 says what building it changed.

Evidence labels: **RUN** (measured here, against the published 5.28.2 packages unless the line says otherwise), **READ** (in the source, `file:line` at `9d994a4b`, or in the wiki at

[`STEP_PHASE_PLAN.harness/`](STEP_PHASE_PLAN.harness/README.md).

A name like R01, X04, L07 or B04 is a test in one of the harness's four suites (Reqnroll, plain xUnit v3, LightBDD, BDDfy), and each suite's dump shows it call by call. `matrix/L01` is a test
in the adapter matrix, which runs the same shapes on NUnit, MSTest, TUnit, xUnit v2 and v3 and Reqnroll on four frameworks. `review/Q05` is a test in the third review's probes, `review4/M01` in the fourth's, `review5/H01` in the fifth's, and `review6/S01` in the sixth's.

#224 reports that a `[GivenStep]` nested in a When step moves the test's phase to Setup and leaves it there, so the rest of the When step's calls are recorded as Setup. It asks for
`StepCollector.StartStep` to set the phase for a top-level step only. The report is right and reproduces as written (R00), and the one-line fix does fix that case. It is still the wrong place to stop,
for four measured reasons:

1. **It breaks shapes that work today.** A `[Step]` method, which has no keyword, that wraps `[GivenStep]` and `[WhenStep]` methods: the wrapped steps are not top-level, so their calls go from Setup and
   Action to Unknown (X04, X05). And a Given still running when a When starts, as in `Task.WhenAll(Given(), When())`: the When is filed under the Given, so it and all that follows go from Action to Setup (X09,
   X10, X21). Fifty recorded phases that are right today go wrong, in 12 of the plain suite's 36 tests. The rule has to be about the keywords above a step in its own flow, not about its depth in the test's stack.
2. **It leaves LightBDD no better, and the issue holds LightBDD up as the model.** No LightBDD cell comes right, and six move from one wrong answer to another. In a plain LightBDD scenario every call a non-HTTP
   tracker makes reads `Unknown`, and every HTTP call reads `Unknown` once the first When call has gone out (L01). So `TrackDuringSetup = false` on a non-HTTP tracker does nothing there (L11), and in the repo's
   own LightBDD example 2 of the 14 test-side calls carry no phase.
3. **It leaves #195,** the same scenario family: an `And` or `But` after a When or a Then records Setup (R06). `But`'s write is that same line of `StartStep`, and `And`'s is the Reqnroll hook's at `:95`, so
   #195's own suggestion does not fix `But` on its own either (F8).
4. **It leaves the boundary alone.** The Setup partition depends on the boundary, and the boundary lives in two private fields of an HTTP handler. A handler shared by two tests draws it for whichever runs first (R11, L07,
   B07), a Given with no HTTP call gets none (R18, L10, B09), a When with no HTTP call gets it late (R19, L09, B08), and a suite of step attributes never gets one at all, though the option's own doc comment calls
   `[WhenStep]` "equivalent to StartAction()" (X01, X06).

The defect underneath: **nothing owns a test's phase.** A phase is a fact about a test, and it is stored as a value of an `AsyncLocal` that eight paths write, several sharing a statement or a word table, each writing to a different
flow. Which reader sees what then depends on the adapter, on whether a step is sync or async, and on which call came first. The plan gives the test an owner for that decision, one rule for what moves it, and has every adapter go through that. Each flow goes on holding what it reads, as it does today, and §5.9 says why.

## 2. Where it stands today

### 2.1 Who writes the phase

`TestPhaseContext.Current` is an `AsyncLocal<TestPhase>` (`TestPhaseContext.cs:11-18`). 28 source files decide whether to record a call from it through `PhaseConfiguration.ShouldTrack`, and 40 read or write it (READ,
`git grep -l` of `PhaseConfiguration.ShouldTrack` and `TestPhaseContext\.Current` over `src/*.cs`). An `AsyncLocal` write reaches the code the current flow runs next, and child flows, and never reaches the caller of an async method. So where each writer stands
decides how far its write goes:

| Writer | When | How far the write goes | Its word table |
|---|---|---|---|
| `StepCollector.StartStep` for a woven step (`:103-118`) | any step with a keyword, at any depth | the caller's flow, as the weaver calls it from the method's stub (`StepWeaver.cs:440-459`): to the end of the nearest enclosing async method, or to the test if there is none | exact case: `Given`, `But` Setup; `When`, `Then`, `ButWhen` Action; anything else, no write |
| `ReqNRollTrackingHooks.BeforeStep` (`:95`), then `StartStep` (`:103`) | every Gherkin step | the hook's flow, which Reqnroll carries into the binding (RUN, R05) | `ResolvePhaseFromStepType` on the keyword as written, then the table above |
| `BDDfyStepTrackingExecutor.Execute` (`:28`, `:53`), and `StartStep` (`:36`) | every BDDfy step, back to `Unknown` after it | `Execute`'s flow, and the step's body | `ResolvePhaseFromStepType` on `Given`, `When`, `Then` |
| `StepTrackingStepDecorator.ExecuteAsync` via `StartStep` (`:28`) | every LightBDD step, at any depth | nowhere that matters: LightBDD's keywords are upper case (`GIVEN`), so the exact-case table never matches (RUN, L01) | none in effect |
| `LightBddTestTrackingMessageHandlerOptions.GetTopLevelStepType` (`:36`) | inside the HTTP handler's fetcher, until the boundary is drawn | that one `SendAsync` | `ResolvePhaseFromStepType` on the top-level step's name |
| `TestTrackingMessageHandler.InjectImplicitActionStartIfNeeded` via `StartAction` (`:473`) | a handler's first call after a setup call | that one `SendAsync` | a prefix test of its own (`:462-464`) |
| `StartSetup()`, `StartAction()` (`TrackingDiagramOverride.cs:93`, `:116`, and each adapter's, which reach those with a test id) | when the test calls them | the caller's flow | none |
| A consumer's own write to `TestPhaseContext.Current` (public; #195's workaround, and the wiki's recipe for fixture operations, `Tracking-Custom-Dependencies.md:677-704`) | any | the caller's flow | theirs |

Those eight paths are 16 assignment statements in 9 files (READ). A fourth word table is in ingest: `IngestAttribution.PhaseForStep` (`:445-455`), where And, But and `*` inherit, and `BuildStepWindows` (`:476`) looks at level 0 alone.
**It is the one place in the repo that already has the right rule for And and But, and for nesting**, and Kronikol4J's Cucumber adapter has the first of those too (`GherkinPhase.java`). The same scenario reads differently in-process and ingested.

### 2.3 What a wrong phase costs

- `TrackDuringSetup` and `TrackDuringAction` drop calls on it, in every tracker (R08). The action under test can vanish.
- `SetupVerbosity` and `ActionVerbosity` choose a call's note on it.
- `kronikol query … --phase` and `--group-by phase` report it, and a call's `phase` is in the data file.
- The report contradicts itself. In R00 the order is drawn after the boundary, in the Action part of the diagram, and its data says Setup.
- The service card's phases follow it (READ, `CallGraphBuilder.cs:51-53`; RUN, `matrix/S01`). A call with no phase of its own, such as the service's downstream call while it serves `POST /orders`, takes its parent's. So `POST /orders` and everything under it count as setup in `effectivePhases` and `phases`, in `service.json`.

## 3. Findings the issue does not state

- **F1. How far a nested keyword reaches depends on sync or async.** An async When step's nested Given stops at the end of that step (X01: `x01-after-when-step` Action). A sync When step's goes on into the test (X03: Setup, until the next keyword). A keyword-free async step between them stops it (R16). Nothing in a test's text tells the reader which they have. The same is true of a Given in a lifecycle method: a plain call in the body reads Setup after a sync or Task-returning `[SetUp]`, and `Unknown` after an async one (`matrix/L01`).
- **F2. On LightBDD the ambient phase is never set in the test's flow.** The message column of L01 is `Unknown` for every call. The decorator passes `GIVEN` to a table that compares `Given` (READ, `StepTrackingStepDecorator.cs:20`, `StepCollector.cs:106`), and its write would stop at its own async frame anyway. The HTTP column reads Setup and Action until the boundary, and `Unknown` after it (L01: `l01-when-and`, `l01-then`), since the fetcher's write is the only source and the handler stops calling the fetcher there (`TestTrackingMessageHandler.cs:452`). The wiki says LightBDD's detection is automatic (`Phase-Aware-Tracking.md:21`). In the repo's own LightBDD example, 2 of the 14 test-side calls have no phase (RUN, `results/examples/base/LightBDD.xUnit2/phases.txt`).
- **F3. So LightBDD's phase options do nothing on a non-HTTP tracker.** L11's message tracker has `TrackDuringSetup = false`, and its setup message is recorded. Nor can a LightBDD suite's `SetupVerbosity` apply at capture: the phase is `Unknown`, so variants are made and picked by position, which needs a boundary (F4).
- **F4. The boundary is per handler instance.** `_wasInGivenSection` and `_actionStartInjected` (`TestTrackingMessageHandler.cs:38-39`) are never reset, and `_lastStepType` beside them is written and never read. Of two scenarios on one handler, the second has no boundary, and so no Setup partition (R11, B06 and B07). On LightBDD it also has no phases at all (L07: every call `Unknown`), as the closed gate stops the fetcher. Any client held in a fixture or a static field shares its handler this way. Under parallel scenarios the fields race (RUN, `review/rev3-parallel`: 1 of 8 fetcher tests with a marker at 5.28.2, 8 of 8 on the patch).
- **F5. The boundary needs HTTP calls in the right steps.** It is drawn at a handler's first non-setup call after a setup call. A Given that only seeds a database or sends a message has no setup call to the handler: no boundary, no partition (R18, L10, B09). A When with no HTTP call is drawn inside the Setup partition (R19, L09, B08), and a When with no HTTP call followed by an `And` waits for the Then (R20, L09). The ingest path draws it from the steps (`IngestPipeline.cs:1358-1369`).
- **F6. A suite of step attributes never has a boundary.** `StepTrackingOptions.WhenTriggersAction`'s doc comment says "equivalent to StartAction()" (`StepTrackingOptions.cs:15`), but `StartStep` writes the phase and logs no marker, and `XUnitTestTrackingMessageHandlerOptions` sets no fetcher. So `SeparateSetup = true` draws nothing (X01, X06: only the tests that call `StartAction()` have a boundary). And `PlantUmlCreator.cs:214` reads no boundary as "everything is action", so a service-side call's Setup variant is never used: `SetupVerbosity` is ignored for those calls in such a suite.
- **F7. Four word tables disagree.** `StartStep` is exact-case and leaves And alone. `ResolvePhaseFromStepType` (`PhaseConfiguration.cs:55-69`) is a case-insensitive prefix test: And and But are Setup, and `ButWhen` is **Setup**, as it starts `BUT`, where `StartStep` makes it Action. The handler's test is a third, and ingest's a fourth, where But inherits.
- **F8. #195's suggestion does not fix `But` on its own.** It asks for the phase from `StepInfo.StepDefinitionType` at `BeforeStep:95`. But `StartStep` runs next at `:103`, with the keyword as written, and its table turns `But` to Setup (READ, `StepCollector.cs:109`). The reporter's workaround works because their hook runs after both. `And` would be fixed, and `But` not (INFERRED). The two issues want one edit.
- **F9. And and But read Setup by design, on paper.** `Phase-Aware-Tracking.md` § Step Type to Phase Mapping says they "always map to Setup because in BDD conventions they typically continue the Given context", with `StartAction()` as the override. It lasts one step (ISSUE, #195). The keyword reached the phase by accident: the adapter moved to `StepDefinitionKeyword` for display in 1.20.0, and phase-aware tracking took that value when it was added (READ, `bf37535e`, and `Integration-ReqNRoll-xUnit2.md:511`: "Earlier versions used `StepDefinitionType`", a sentence about the label, which stays true).
- **F10. BDDfy's async steps have no parent for a sub-step to be under.** `BDDfyStepTrackingExecutor`'s `finally` closes the step at its first `await` (#122), so a woven `[GivenStep]` after that is top-level (B04's step tree), and a rule about nesting cannot see it. Top-level or not, B04 stays wrong until the step stays open. That is why R3 is here.
- **F11. The wiki's phase table has more errors.** BDDfy's row says `Assertion` is Setup (`Phase-Aware-Tracking.md:20`); the code and B01 say Action. Its internal diagram shows every adapter setting the phase as a step starts, which LightBDD's never did.
- **F12. An explicit `StartAction()` inside an async method draws the boundary, and its phase ends with the method** (X07: `x07-after-step` Setup, after the marker). "Everything after is treated as action" (`Phase-Aware-Tracking.md:79`) holds for the diagram, not the data. It stays so (§11): the wiki's sentence is what R1 corrects.
- **F13. A step attribute on a method returning `ValueTask` or a value throws `InvalidProgramException`.** It stopped a probe of this plan's, which then had to return a `Task`. It is #226's, and left to it, with F19's weaver half and F20 (Q11).
- **F14. Kronikol4J has #224's write line for line** (`StepCollector.java:87-90`), with no flow to contain it, so X03's shape is every shape there. Its Cucumber adapter has #195 right (`GherkinPhase.java`). For a ledger line (§8).
- **F15. A failing or bypassed LightBDD sub-step closes its parent too.** `StepTrackingStepDecorator.ExecuteAsync`'s `catch` completes the step, and its `finally` then finds the parent active and completes that, as passed (READ, `:34-44`). So the step tree is wrong today, and the rule would read the sub-steps after it as top-level, where they would decide. R1 fixes it (L14). BDDfy's `catch` and `finally` do the same to a woven sub-step's parent (RUN, `review/Z15`), and R1 fixes that too.
- **F16. A tracked call outside a scenario, on a LightBDD handler, throws out of `SendAsync`.** `GetTopLevelStepType` asks `ScenarioExecutionContext.CurrentStep`, which throws outside a scenario (READ, `LightBddTestTrackingMessageHandlerOptions.cs:27`). A handler that has already drawn a boundary has stopped asking, which hides it (RUN, `probes/review/out/*/outside-a-scenario.txt`, under a `TestIdentityScope`). R2's per-test gate asks again for each new test, so R2 has the handler guard its call. The fetcher's own throw stays: two facts pin it (`ShouldThrowWhenStepTypeFetcherCalledOutsideScenarioContext`), and the first attempt at this guard, inside the fetcher, broke them.
- **F17. `setup` is one of LightBDD's own step types and has no phase** (L13: `Unknown` for both trackers, and no boundary).
- **F18. BDDfy's steps with no keyword read `Unknown`.** `TearDownWith`, and the `TearDown*`, `Setup` and `*Context` methods the scanner finds by name, have no keyword, and `BDDfyStepTrackingExecutor.cs:28` writes `Unknown` for them, so a teardown after the boundary reads `Unknown` (B10). §2.2's first draft said BDDfy has no such step.
- **F19. A skipped sub-step closes its parent too.** F15's twin, in the weaver. `BypassStep` pops the step, and the stub's return path then completes again, sync (`StepWeaver.cs:319`) and async (`:527`), which closes the step above it. So a real sub-step after a skipped one is filed at the top level with a bar of its own, and it moves the phase (X30: Setup, for the rest of a When). #226's draft has this as its F4.
- **F20. A Task step that is not `async` and throws before returning never closes.** The weaver has a catch on its sync path (`StepWeaver.cs:297`) and none on its Task path (`:527`). If the test catches the exception and goes on, every later step is filed under the open one, and the test's step list comes out empty (RUN, X25), or stops at the step before it (`await Assert.ThrowsAsync(() => GivenGuarded())` then a When, X33). #226's draft has this as its F3.
- **F21. A step left running makes the wrong step close.** `CompleteStep` closes the stack's top, whichever step is completing (READ, `StepCollector.cs:124-154`). A sync Given that starts a worker step and returns closes the worker and stays open itself (review/B01, review/Q01). Today that only misfiles the tree. Any rule that asks whether a step is still open must not ask `EndTime` (§5.2).
- **F22. Under runtime async there is no stub.** On .NET 11 RC3 with `<Features>runtime-async=on</Features>`, an `AsyncLocal` write inside an async method still does not reach its caller, whether it suspends or not (RUN, `probes/runtime-async/`). Today every async `[Step]` throws `InvalidProgramException` there. #226's weaver brackets such a method in its own frame, with no stub and no `CompleteStepAsync`, so a step's write reaches its body and not its caller: a plain call in the test body after an async When keeps the phase the test body held (RUN, `results/net11-on226.txt`), though each step's own calls read right. This plan leaves that to the day runtime async is on by default (§9).
- **F23. ## 4. The underlying problem

A step's keyword does two jobs. It is a label, which the step list and the step bar print. And it is an instruction to move the test's phase, which only makes sense for the steps that divide a test into its setup and its action. `StartStep` treats every keyword as both, at any depth, because it has no notion of the test's phase to consult: it has a stack of the test's steps in `TestStepState`, a per-test object, and it writes the phase somewhere else.

Everything measured here follows from where that somewhere else is:

1. **The phase lives in a flow, not in a test.** So how far a write goes depends on who made it and how (§2.1), so the same shape reads differently by adapter and by sync or async (F1), and "the phase before this step" cannot be read back, which is why no adapter could do `And` properly: on LightBDD each step's flow sees nothing of the last (F2), and a table given only the keyword has to guess (F9). This plan moves the decision to the test and leaves the value in the flow, for the reasons in §5.9.
2. **Nothing compares a keyword with what is above it.** So a label moves the phase (#224), and nothing is there to set it back. Setting it back when the step completes is not available: that write runs in `CompleteStepAsync`'s continuation, and an `AsyncLocal` write there never reaches the caller (RUN, `results/restore-at-complete.txt`). The stub could set it back as it returns, and that gives a timeline that alternates (§5.9). So the phase should not move.
3. **Each path has its own table** (F7), so #195 is written twice, and a fix to one line leaves the other (F8).
4. **The boundary is read off a reader.** An HTTP handler sees only its own calls and holds its findings in its own fields, so whether a test has a boundary depends on its handler's lifetime and on which steps make HTTP calls (F4, F5, F6). The steps, which know, draw nothing.
5. **The step stack is the test's, not the flow's.** A step left running is filed as the parent of whatever starts next, so any rule that asks "what is above this step?" of that stack is wrong for `Task.WhenAll(Given(), When())` (X09, X10, X21), and it closes the wrong step (F21). The first cut of this plan asked the stack, and its third asked `EndTime`.

The issue's line treats layer 2 with depth. It is the right idea with the wrong test, and it leaves 1, 3 and 4. The ingest pipeline shows the shape of the answer: a phase per test, read from the steps that divide it, with `And` from the step before (`IngestAttribution.cs:445-489`). The in-process path has the data to decide the same way, and has never used it.

## 5. The design

### 5.1 The rule

> A test's phase is moved by the outermost step open in its flow that says anything about phases. A keyword under it is a label. A step on a flow that is not the test's own keeps its phase to itself.

> A call reads what its flow holds, as it does today.

`TestStepState` gets the test's phase, and `StartStep` decides from that and from the steps open in the current flow, once. A step that decides writes its flow, as every step does today, which for a woven step is the caller's:

| Open in this flow | The step starting | Today | After |
|---|---|---|---|
| none | `Given` | Setup | Setup |
| When | `[GivenStep]` | Setup, and the rest of the When (#224) | no move |
| Given | `[WhenStep]`, `[ThenStep]`, `[ButWhenStep]` | Action, and the rest of the Given | no move |
| `[Step]` | `[GivenStep]`, then `[WhenStep]` | Setup, then Action | the same: `[Step]` says nothing, so they decide (X04, X05) |
| Given, `[Step]` | `[WhenStep]` | Action inside the `[Step]` (R16) | no move: the Given is above it |
| none | a LightBDD `AND` | `Unknown` | the phase before it |
| none | an `AND` with nothing before it | `Unknown` | says nothing, so a typed sub-step under it decides (L15) |
| none | `[ButStep]` | Setup | Setup, as documented (X06) |
| none, with a Given still running in another flow | `[WhenStep]` | Action (X09, X10, X21) | Action: the Given is not above it, and the Given's own later calls still read Setup, as they do today |
| none, on a detached flow, or a thread or a server's flow with only a `TestIdentityScope` | `[WhenStep]` | Action in that flow | the same, and it moves neither the test's phase nor its boundary (`matrix/T01`, `matrix/N30`, `matrix/S31`, `review4/G03`) |
| a closed step this flow was forked inside | `[ThenStep]` | Action in that flow | the same, and it moves nothing of the test's (`review/Q05`, `review/C01`) |

"Says anything" depends on who speaks. A step attribute, or a step made by hand through the public overloads, says what it says today: the exact words of `:103-118`, with `And` saying nothing (`PhaseOfAttribute`), so no consumer's hand-made step changes meaning (`review5/A01` to `A04`, `review4/B03`, `B04`). An adapter's word goes through `PhaseConfiguration.PhaseOfStep`, compared case-insensitively:

```csharp
internal static TestPhase? PhaseOfStep(string? keyword, TestPhase previous) => keyword?.ToUpperInvariant() switch
{
    "GIVEN" or "SETUP" or "BUT" => TestPhase.Setup,   // SETUP is LightBDD's own step type (F17)
    "WHEN" or "THEN" or "BUTWHEN" => TestPhase.Action,
    "AND" => previous,   // the flow's phase, or the test's if the flow holds none
    _ => null   // no keyword, or a step type of the suite's own: leaves the decision to the steps under it
};
```

Why not "top-level": a keyword-free wrapper is a real shape (X04). `[Step]` is documented as having no phase transition of its own (`Step-Tracking.md:78`), which says nothing against the keywords under it, and they have always moved the phase. Why not "any keyword above": a LightBDD suite can define its own step types, and one that means nothing to phases should not stop the typed sub-steps under it. Why not "above it in the test's stack": a step left running is not above what its caller starts next (X09, X10, X21), and the first cut, which asked the stack, regressed all three.

Why the flow keeps the value: four cuts of this plan had `TestPhaseContext.Current` read the test's decision, which closes every stale flow the harness has, and each review found more of what that flips: a detached worker reading the phase of the test that started its host, a poller the wiki's own recipe silenced, a response read apart from its request, a tear-down dropped under `TrackDuringAction = false` (§5.9, Q12). #224, #195 and LightBDD need none of it.

### 5.2 `StepCollector` and `TestPhaseContext`

**As executed:** #223's R1 (each framework step has an id, and `CompleteFrame` closes it) and #225's R1 (`FlowStep`, the flow held in `StepCollector`) reached this code first. So the chain below, `Without`, `LeaveCompletedStep`, `CompleteDownTo` and `OpenStepCount` went, and the rule stands: `OpenStep` decides as sketched, over two walkers on #225's flow. A framework's own step decides wherever it runs, so `OutlivedStepSaysPhase` holds a step with no frame alone (review 4, F1 in §12).

```csharp
var named = phaseKeyword is not null || FrameworkNamesThisFlow();
var flowPhase = TestPhaseContext.Current;
…
var says = phaseKeyword is not null
    ? PhaseConfiguration.PhaseOfStep(phaseKeyword, flowPhase != TestPhase.Unknown ? flowPhase : state.Phase)
    : Options.WhenTriggersAction ? PhaseConfiguration.PhaseOfAttribute(keyword) : null;
step.SaysPhase = says is not (null or TestPhase.Unknown);
if (step.SaysPhase && !OpenStepSaysPhase(testId))
{
    phaseNow = says!.Value;
    if (named && !OutlivedStepSaysPhase(testId))
    {
        state.StepsSetPhase |= frameworkStep;
        state.Phase = phaseNow;
    }
}
…
EnterFlow(testId, step);
…
if (phaseNow != TestPhase.Unknown)
    TestPhaseContext.Current = phaseNow;
```

That replaces the `switch` at `:103-118`. `TestPhaseContext` does not change, so every tracker still reads what it read, and no tracker changes. A flow's own write stays its own: `StartSetup()` scoped to a helper (X28), the wiki's fixture recipe and its `Current = Unknown` reset (`review/D01`), a poller it silences (`review4/F02`), a direct write before an `And` (`review/G04`). The test's phase is read for two things, an adapter's `And` on a flow that holds nothing, and R2's boundary.

**Nothing fills a flow.** An earlier cut had a step with no keyword copy the test's phase into a flow reading `Unknown`. The review broke it with a Given in `InitializeAsync` and keyword-free steps on a `TrackDuringSetup = false` client (`review/D10`, `G06`, `G07`, `D01`). A plain call before the action stays as it is today.

**The steps open in a flow.** `CurrentFlowStep` is a private `AsyncLocal` chain, and `OpenStepSaysPhase` walks it.

- `StartStep` adds the step to the chain, in the flow it runs in, which for a woven step is the stub's, so the caller's.
- `CompleteStepAsync` stops being `async`, keeping its signature, so the weaver's call (`StepWeaver.cs:530`) is unchanged. Its first line runs in the stub, before the stub returns (`StepWeaver.cs:521-532`), and takes the step off the chain in the caller's flow. Its `await` moves to a private method. So a step left running is above nothing its caller starts next, and the step's own body, which captured its context before that, still has it above.
- Whoever completes a step takes its own step off its own flow's chain, whichever step the stack popped (`LeaveCompletedStep`, F21), and takes off the step the stack really closed if it is on that chain too (`review5/R09b`). So a closed step still on a chain means this flow was forked inside it and outlived it, and a keyword there is the flow's own (`OutlivedStepSaysPhase`). The one exception is a hand-made step closed from another flow: its chain cannot be reached from there, so the keywords after it on this flow move nothing of the test's, with phases right and no boundary, which is what a plain suite has today (`review6/C02`).
- A node's parent is the flow's head, whichever test the head is for, so a hand-made step for another test's id inside a Given does not lose this test's chain (`review4/F05`), and a completion takes off its own node and leaves another test's above it, so neither does the other order (`review6/I02`, `I03`). A step the stack closed that was not this completion's goes from the chain with whatever is above it (`review5/R09b`).
- A bypassed step has closed already. Its stub now returns with no completion, where it used to close the step above it (F19, X30, X36, X37), which is the contract of #226's wrapper, and a step bypassed by hand under a woven parent leaves the parent to close (`review/A01`, `review5/H01`, `H02`, `H13`), as `OutlivedStepSaysPhase` passes over a bypassed node and `LeaveCompletedStep`'s walk does too. `BypassStep` also takes its own node off the chain, and either that or the walk's check does the job (§6).

The step tree stays on the per-test stack, as it is. That is #225's to correct (§9).

**The weaver** changes too, if #226 has not landed. A Task stub that is not `async` gets a catch, as its sync path has (F20, X25, X33). It gives a handler the method ended in a real end first, as Cecil reads a null `HandlerEnd` as the method's end and the appended blocks would land inside it (X32: `InvalidProgramException`, on the first four cuts of this plan), turns a `tail.` prefix into a `nop`, and adds a hidden sequence point, each as #226's wrapper does. The sync path gets the first two as well, which it lacks today (`review4/S02`: `InvalidProgramException` on a sync step ending in a handler, and on an F# tail call in Release). The bypass path on both ends in a plain `ret`, and a `SkipIf` member's read gets a try whose catch fails the step, so a getter that throws leaves no step open (`review/G14`, `review5/H05`). The read stays after `StartStep`, where it is today: a getter's tracked call belongs to its step, and a getter can ask what phase it is in. The previous cut read it first, and a When's `Current != TestPhase.Action` then skipped the act (`review6/S01` to `S11`). All of this is what #226's wrapper does in its own way, so if #226 lands first, none of it is here (Q11). With no `SkipIf`, an `async` method's IL does not change.

Two small internals go with it:

- An internal overload of `StartStep` takes `phaseKeyword`, the word a framework adapter gives for the step's phase, and `frameworkStep`. The public overloads pass null and false. A step attribute's keyword counts while `WhenTriggersAction` allows it; an adapter's always does. That keeps what the option does today for adapters (it never stopped their writes) and states it (R21).
- `NotePhase`, called by `StartSetup` and `StartAction`, tells the test's state, so an `And` after an explicit phase continues that.

A step with no test id returns before any of this, as it does today (`:57-58`), so it writes no phase before or after.

### 5.3 Reqnroll: #195

`BeforeStep` gives the keyword as written as the step's label, and `StepInfo.StepDefinitionType`, which Reqnroll resolves And, But and `*` to, as its phase. Line 95 goes, as `StartStep` does it. So F8 does not arise: the table never sees Reqnroll's `But`. `StepDefinitionType` is on the floor version, 3.0.1, which `Kronikol.ReqNRoll.Core.csproj:17` compiles against (READ). `ReqNRollTestContext.CurrentStepType` stays the keyword as written: it is public, and after R2 no adapter's boundary depends on it.

`[ButStep]` stays Setup, because that attribute is documented as the Setup flavour, and `[ButWhenStep]` exists for the other. A framework's `But` is a continuation, so it never reaches that table. A nested Gherkin step through an injected `ITestRunner` fires the hooks once and is a label (RUN, `matrix/N01` to `N08`, on all four frameworks).

### 5.4 LightBDD

The decorator passes the step type as `phaseKeyword`. The case-insensitive table reads it. Its write reaches the step's body, and not the next step, since `ExecuteAsync` is an async method, and that is enough: the test holds the phase.

- `AND` reads the test's phase from `TestStepState`, as its flow reads `Unknown`.
- A step with no type reads `Unknown`, as it does today (L12).
- `setup` reads Setup (L13). A suite's own `BUT` (`UpdatePredefinedStepTypes`) continues, as a Gherkin `But` does: the decorator maps it to `AND` for the phase, and its label stays.
- The decorator's `finally` goes, and a passing step completes after the `try`, so a failing sub-step closes itself alone (F15, L14).
- `GetTopLevelStepType`'s write stays for one path: `ReportWritersConfiguration.CreateStandardReportsWithDiagrams` is public, `[Obsolete]`, and registers no step decorator (READ, `ReportWritersConfigurationExtensions.cs:22-24`), and there the fetcher is the only source. It writes while no framework step has decided (`FrameworkStepsSetPhase`), so where the decorator runs it fires only before any step has said anything: an `AND` first (L15, L16).

### 5.5 BDDfy

`Execute` passes its keyword as `phaseKeyword`, and its write at `:28` goes, as `StartStep` does it, but for a story with no test id, which `StartStep` skips and which keeps its write (`review5/F01`), and for a step with no keyword at the top of a story, which writes `Unknown` as it does today, whatever the flow held before the story (B10, F18, `review6/B18`, `B20` to `B23`). At `:53` a step at the top of a story ends in `Unknown`, as it does today, so a tear-down or a call after the story reads `Unknown` whatever the flow held before the story (`review4/B01`, `B02`, `review5/B15` to `B17`). Under a step that said a phase, a story is a label, and the step gives back what the flow held, so the rest of a woven Given goes on reading Setup. A `Setup` method, before any step has said anything, stays `Unknown` (Q10). Its `catch` and `finally` no longer close a woven sub-step's parent (F15).

### 5.6 R2: the boundary at the step

`StartStep` draws the boundary the first time a test's steps go from Setup to Action, after the step's bar:

```csharp
if (named && !OutlivedStepSaysPhase(testId) && (frameworkStep || !state.StepsSetPhase))
{
    if (frameworkStep && !state.StepsSetPhase)
    {
        state.ActionStepSeen = false;
        if (!state.ExplicitBoundaryDrawn && !state.ClientDrewBoundary)
            state.ActionStartDrawn = false;
    }

    startsAction = says == TestPhase.Action && (state.Phase == TestPhase.Setup || (frameworkStep && state.CallInSetupStep))
        && !state.ActionStartDrawn && !state.ActionStepSeen;
    state.ActionStepSeen |= says == TestPhase.Action;
    state.ActionStartDrawn |= startsAction;
    if (startsAction && frameworkStep)
        state.BoundaryStep = step;
    …
}
…
if (startsAction)
    DefaultTrackingDiagramOverride.DrawBoundary(testId);
```

It runs outside the state's lock. Bar then boundary is the order `PlantUmlCreatorTests.Setup_partition_survives_step_delimiter_bars` pins, so the common picture does not move. The boundary falls where it does today when the When's first call is HTTP, and earlier when it is not (F5). `CallInSetupStep` is what the handler saw, so a LightBDD `And` first, which says nothing, keeps the boundary it has today (L16). Never once an Action step has run: When, Then, Given, When would otherwise put a Setup partition over the first act, and the page's Setup filter would hide it (`review/E05`; on BDD adapters today, `review/Q13`). A framework's steps own the boundary: a woven keyword before its first step does not count as an act, and one on a flow with nothing open above it, once its steps have begun, is the flow's own (`review5/R04`, `R05`, `B02`, `B16`). A boundary a woven step drew before the framework's first step gives way to the framework's (`review6/R41`, `B24`).

Tests with a boundary go from 42 of 85 to 78 of 85 (RUN). The seven left: six have no Setup step followed by an Action step (R13, X13, X17, X26, X29, L08), and X20 has them with the option off. A Given with no tracked call draws no partition, as `hasSetupTraces` finds nothing inside it (RUN, `review/E01`, `Z10`), and a Given whose calls were all dropped now draws none either (`review/E90`), where a Given that kept a message beside a dropped call has that message in its partition (`review/E02`). The handler's three fields go. `InjectImplicitActionStartIfNeeded` remains for a test whose framework starts no steps: a custom `CurrentStepTypeFetcher` (public option), or LightBDD with no decorator. What it has seen moves to `TestStepState`, so it is the test's and not the handler's (F4), and every fact of the handler's "Implicit setup step detection" block holds unchanged (RUN). The handler asks the fetcher only while no framework step of the test has decided a phase and this client has not passed the boundary, as on the `[Obsolete]` LightBDD path the fetcher is each client's only source of a phase (`review5/L01`, `L07`), and one boundary is drawn for the test. A shared handler now asks again for each new test, where it used to stop for good at its first boundary, so the handler guards the call: a fetcher that throws anything, as LightBDD's does outside a scenario and as one written for a single test can on the next, counts as no step type (F16, `review6/F2`). A call must not fail for want of one. A second client's first call past a boundary that is already drawn still reads Action, as the fetcher named it (`review6/F1`).

**An explicit `StartAction()` overrides a step's boundary while that step is open, and only the first one counts** (Q5). `PlantUmlCreator` takes the last boundary a test logged, and only that one acts. - Every other reader tested excludes it: `Failures.md`, `Failures.jsonl`, `service.json`, `History.run.json`, and 42 of 44 `kronikol query` calls are identical, 14 of those answering "none" on both sides, and 2 differ in alignment or sizes (RUN, `review/rev3-readers`, `results/query-diff.txt`). ### 5.7 R3: a BDDfy async step stays open

**As executed:** this shipped in 5.29.3, with #223's R1, through `CompleteFrame`. R3 has no source of its own, and its facts went in with R1.

`BDDfyStepTrackingExecutor.Execute` returns the step's task wrapped so that the step closes when it ends, and BDDfy's `AsyncTestRunner.Run` waits on what `Execute` returns (READ, TestStack.BDDfy `AsyncTestRunner.cs`). A sync step, and an `async void` step, close as they do today.

That makes B04's woven `[GivenStep]` a sub-step, so the rule covers it, and it should record #122's "assertions made after the await" (INFERRED: no probe asserts, so §6 has the fact). An async failure now reads `[Failed]` (RUN, `review/Z04`, `Z13`). Its own bar goes with it, as a sub-step has none (`results/5.28.2/bddfy-xunit3.txt`, "Given Woven given"). It does not touch #122's durations, which are BDDfy's own stopwatch (`StepExecutor.Execute`), so #122 stays open for them.

### 5.8 What does not change

- **No public member is added, removed or renamed.** The overloads are internal, the handler's fields private, and `CollectedStep` is a private class.
- **`TestPhaseContext`.** Not a line of it, so `TestPhaseContextTests` stands as it is, a consumer's own write still wins until the next step that decides in that flow, and no tracker changes.
- **The phase of a top-level Given, When or Then** on a flow the framework names, on every adapter that had one. **`[ButStep]`**, and `WhenTriggersAction` for a step attribute. And and But do change, which is #195.
- **Keywords as written, sequencing, step lists and step bars,** but for §5.7, F15, F19 and F20, where a step moves under its real parent.
- **`PhaseConfiguration.ResolvePhaseFromStepType`'s** answers but one: it is public and pinned, and `GetTopLevelStepType` still uses it, and it reads one word with nothing before it. `ButWhen` becomes Action (F7), and its doc comment says what And and But mean there.
- **Ingest.** It stays on its own table. The two agree on Given, When, Then, And and ButWhen, and differ on purpose on But, which inherits in ingest, and on `setup`, which no Gherkin step is. Context, Action, Outcome, Conjunction and `*` are ingest's alone, and a word neither knows reads null in-process and `previous` in ingest. A fact covers the shared five and pins the differences (§6).
- **Service-side calls.** A call the service under test makes runs in the server's flow and stays `Unknown` at capture, with its parent's phase derived later, on TestServer and on Kestrel (RUN, `matrix/S01`, `S21`, and the example suites). The service card follows the fix through that derivation. With `PreserveExecutionContext = true` the flow reaches the server, today and after (`matrix/S11`).

## 9. Risks

- **A step left running, and the step tree.** `var g = GivenSlow(); await WhenFast(); await g;`, or a top-level `Task.WhenAll(Given(), When())`: the phases are right (X09, X10, X21), as they are today, and the boundary falls at the When. The report's step tree still files the When under the Given with no bar of its own, as the stack is the test's. So phase and tree disagree there, as they do today. #225 corrects the tree. Under a step the same stack closes the wrong step (F21), and two things stay from that: a running sibling closed by another's completion reads its own later sub-step as a decider (`review/F01`: Setup at both versions), and a background Then loop forked from a Given whose completion went to a poll can read Setup in some polls where today they read Action (`review/Q05`, `M02`). Each needs a step's own completion recorded apart from the stack, which is #223's and #225's. A hand-made step completed from a `DisposeAsync` with an await has the same limit (`review4/F04`), and a skip beside a sibling left running no longer closes that sibling by accident, so the steps after it nest under it and lose their bars (`review6/B05`).
- **A step that never completes pins its flow.** A hand-started Given never completed (`review/G02`, `review5/H04`, `E03`: a consumer's bug, and the changelog says so). Every later keyword on that flow is a label, so a When reads Setup, where today it reads Action. A `SkipIf` getter that throws no longer does this (§5.2).
