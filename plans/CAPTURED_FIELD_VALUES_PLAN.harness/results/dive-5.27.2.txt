================================================================================================================
THE DEFECT, CONFIRMED, AND NOT RELEASE-ONLY AT 5.27.2
================================================================================================================
GetStateFieldOriginalName (AssertionWeaver.cs ~2414) reads ANY field named <name>... as "name". A primary-constructor
parameter is the class field <name>P, so the lambda arm (~1976-1993) captures it with StateField = Class::<name>P and the
emit (~3192) writes `ldarg.0; ldfld Class::<name>P`. Inside MoveNext, ldarg.0 is the state machine, so the field is read
at the wrong offset of the wrong object. The raw-name arms (lambda ~2029-2039, ldtoken ~2091-2101, standalone ~2114-2160)
likewise never check that the field was read off `this`: another instance's field becomes this.field, and in a static
method ldarg.0 is the first parameter.

The issue (filed at 5.12.0) calls this Release-only, because Debug did not weave the awaited statement's values (#212).
At 5.27.2 Debug weaves them too, and Debug mis-reads, and in one shape crashes.

Every verifier error the weave added in this dive is StackUnexpected: the base `ldarg.0`/`ldloc` pushed is the wrong
type for the `ldfld`. Exact text, P1 Release:
  P1/<AssertionPasses>d__5.MoveNext: StackUnexpected: Unexpected type on the stack. (Offset 242, Found address of
  '[Probe213_P1_Release]P1+<AssertionPasses>d__5', Expected ref '[Probe213_P1_Release]P1')
(Debug says "Found ref" where Release says "Found address of": a class state machine against a struct one.)

CRASH CASES
================================================================================================================
57 of the 216 runs killed the test host, each time and in every round: exit 0xC0000005 (STATUS_ACCESS_VIOLATION), with
  Fatal error.
  System.AccessViolationException: Attempted to read or write protected memory. ...
     at System.Runtime.CompilerServices.CastHelpers.StelemRef(System.Object[], IntPtr, System.Object)
     at P6+<AssertionPasses>d__2.MoveNext()
  P1 Debug; P6 Release and ReleaseDebugPlus; all eight P12 variants in Release and ReleaseDebugPlus.
No hangs, and no crash anywhere but this value-load. Two more cases change the outcome without crashing: P14 Release
sync and P15.Second (every build) throw NullReferenceException where the unwoven build passes.
Inversion against the issue: P1, the issue's surviving test, crashes in Debug at 5.27.2 and passes in Release (recording
null), while P6 and P12 crash in Release. Whether a shape survives depends on what the state machine holds at the
parameter's offset: the test instance (Debug, <>4__this), the closure (<>8__1), null, or non-object bytes (a crash).

OTHER MIS-MAPPED FIELD KINDS (the brief's last item)
================================================================================================================
  <Prop>k__BackingField: GetStateFieldOriginalName would read it as "Prop", but C# reads an auto or record property
    through its getter (callvirt get_Prop), never by ldfld of the backing field in an assertion, so C# cannot reach it.
  A field of an async lambda's own state machine: P7 and P9. The weave does not scan inside the inner state machine, so
    nothing is captured there.
  Reachable beyond primary-constructor parameters: another instance's field read as this.field (P13 ldtoken arm, P17
    standalone arm), a static method's first parameter used as `this` (P15), an instance field of a parameter read off
    the state machine (P16).

SURPRISES
  - Not Release-only (above).
  - Shapes that never capture the value: P7, P8, P9, P11, and P17(a); P10's `_field` is never captured.
  - A second defect, independent of the receiver: in plain Release a sync closure's base is loaded from a local that no
    longer holds the display class (`ldloc ClosureLocalIndex`, AssertionWeaver.cs ~1788/~3182): P14 Release sync throws,
    and P15.First Release records c._harness for c.
  - Labels hide the wrong value almost everywhere: Shouldly's "Should throw X" drops the lambda, and a subject reads as
    words. Only the values array shows it, so the woven note looks right while the array is wrong.
