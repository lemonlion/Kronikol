Reading of the results (an inference from the IL, the outcomes and the probes; no field offset was measured):
  ldfld of an instance field takes the field's offset in the test class (its place among the class's reference
  fields, which the runtime lays out first, plus the instance's method table word) and applies it to whatever
  ldarg.0 holds. Which test survives therefore depends only on the parameter's place among the class's fields and on
  the state machine's own fields, the same under xUnit v2 and v3: all 14 T1-T7 pairs agree between the frameworks, and
  T7's long and int, which come after the reference fields, leave <third>P where T1 has it (T7 behaves as T1 in every
  build).
  In Debug ldarg.0 is the state machine object, so the read is a field of that object (or what follows its last one):
    T5 (<third>P, the 1st field)    the test class instance, which is the state machine's <>4__this (probe V5: proven)
    T2 (<handlers>P, the 2nd)       an object that prints nothing; consistent with <>8__1, the display class (probe V2)
    T1, T7 (<third>P, the 3rd)      not a pointer (consistent with <>1__state, an int): StelemRef faults
    T6 (<sixth>P, the 6th)          null (probe V6)
  In Release ldarg.0 points into the state machine struct, boxed after the Task.Yield (T1, T5, T6, T7: the crash stacks
  run through AsyncStateMachineBox), still on the stack in T2 (its crash stack runs through AsyncTaskMethodBuilder.Start):
    T1, T7 (the 3rd)                null (probes V1, V7)
    T5 (the 1st), T2 (the 2nd)      not a pointer: StelemRef faults
    T6 (the 6th)                    readable memory that is not an object: the store passes, GetType faults
