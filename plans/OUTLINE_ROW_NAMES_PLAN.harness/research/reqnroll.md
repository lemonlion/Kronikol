Every claim names its source. The tags say how it was established:

- **READ**: read in a file (source, generated code, nuspec, changelog, XML doc).
- **RAN**: produced by a build or a program run in the scratch folder, output kept there.
- **IL**: read from a DLL's metadata and decoded method bodies by reflection, nothing in it executed
  (`reflect/Inspect-IL.ps1`, below). The decoder lists the calls, field accesses and string literals of a
  method, not its branch targets, so control flow read from IL is marked INFERRED where it matters.
- **INFERRED**: deduced, not read or run.

## Answers in brief

1. Kronikol supports **Reqnroll >= 3.3.4** (no upper bound) and builds and tests against **3.3.4** only.
   3.3.4 is also the only Reqnroll in this machine's NuGet cache.
2. For an outline, every framework's generated method creates
   `new global::Reqnroll.ScenarioInfo("<raw title>", <description>, tagsOfScenario, argumentsOfScenario, featureTags, pickleIndex)`.
   Before that it runs one `argumentsOfScenario.Add("<header>", <param>)` per column. The row values,
   the pickle index (as a string) and the Examples tags come in as test parameters. The display name is the
   raw title on xUnit v2 and v3, and `"<raw title> ($p1, $p2, ...)"` on TUnit. No NUnit or MSTest code is
   generated anywhere on this machine, and Kronikol has no Reqnroll adapter for either.
3. Of the nine scratch cases, Reqnroll refuses three at build time: (c) different headers, (e) a duplicate
   header and (g) a header-only Examples. So does a reordered-header case (k). Escapes are decoded before the
   values reach the code. Gherkin builds the pickle name with one `string.Replace` per header, in column
   order, which re-substitutes a value that itself holds a later header's placeholder (case j).
4. The filled pickle is reachable from a running scenario only through **internal** members:
   `FeatureContext.FeatureInfo.FeatureCucumberMessages` (internal) `.Pickles` (public), indexed by
   `ScenarioContext.ScenarioInfo.PickleIdIndex` (internal). Kronikol already reads exactly these by
   reflection in `ExamplesBlockResolver`. 3.3.4 and 3.3.3 have them (since 3.0.0 by the changelog, INFERRED).
   No supported MSBuild property or `reqnroll.json` key turns the embedded pickle data off. It is missing
   only after a generation error, after a project strips the resource, or in a host where reflection-based
   System.Text.Json is off; Reqnroll then reports no pickles and throws nothing. No public member gives the
   row's expanded name.
5. Yes. `ScenarioInfo.Title` is the raw title in every outline looked at (all generated by 3.3.4).
   `ScenarioInfo.Arguments` holds every column of the row, in header order, keyed by the header text as
   Gherkin parsed it (trimmed and unescaped; spaces, non-ASCII and C# keywords kept), with the decoded cell
   strings as values. Applying Gherkin's rule to `Title` and `Arguments` reproduces every pickle name the
   compiler wrote: 13 of 13 outline pickles in the scratch project (RAN).

## 2. What Reqnroll generates for a Scenario Outline

**Surprise:** the brief says generated `*.feature.cs` files are not tracked. In this repository they are.
`git ls-files` lists the five under `examples/` (`ReqNRoll.TUnit/Features/Cake.feature.cs`, `ReqNRoll.xUnit2/Features/Cake.feature.cs`,
`ReqNRoll.xUnit3/Features/{Cake,CakeQuality,Muffins}.feature.cs`), and `.gitignore` has no rule for them. Every build
of those projects rewrites them in place. The Kronikol-101 `Muffins.feature.cs` is byte-identical to Kronikol-scroll-r1's,
and Kronikol-187audit's differs only in line endings (`diff --strip-trailing-cr`).

**Where outlines exist on this machine** (READ, a search of every `*.feature.cs` under `C:/Code` for
`argumentsOfScenario.Add`): only xUnit v3 has one. That is the examples' `Muffins.feature.cs` (in every Kronikol
worktree) plus 10 files in BreakfastProvider's xUnit v3 lane (`Reqnroll.xUnit.V3` 3.3.4). The xUnit v2 and TUnit
examples hold only `Cake.feature`, which has no outline. Nothing anywhere was generated for NUnit or MSTest, and
neither package is in the cache. Their generator providers live inside `Reqnroll.Generator.dll`, whose string
literals include `NUnit.Framework.TestCaseAttribute` and `Microsoft.VisualStudio.TestTools.UnitTesting.DataRowAttribute`
(IL). They are out of scope, since Kronikol has no adapter for them. The xUnit v2, TUnit and placeholder-title
cases were generated in the scratch projects (section 3).

The header every generated file carries, `//      Reqnroll Version:3.0.0.0`, is the assembly version shared by all
3.x packages, not the package version (READ: generated by 3.3.3 at ba972c50 and by 3.3.4 alike).

### b. Is the embedded pickle data always generated? Yes; nothing supported turns it off.

- The MSBuild targets embed the messages whenever the generator wrote them, with no switch (READ,
  `reqnroll.tools.msbuild.generation/3.3.4/build/Reqnroll.Tools.MsBuild.Generation.targets:216-223`):
  `<!-- Embed messages files as resource (required for Reqnroll) -->` ...
  `<EmbeddedResource Include="@(ReqnrollFeatureFile->'%(MessagesFile)')" Condition="Exists('%(ReqnrollFeatureFile.MessagesFile)')">`.
  The props file's feature flags (`ReqnrollUseIntermediateOutputPathForCodeBehind`, `ReqnrollEmbedFeatureFiles`,
  `ReqnrollWarnForObsoleteCodeBehindFiles`, `ReqnrollDeleteObsoleteCodeBehindFilesOnClean`, `.props:37-59`) do not touch messages.
- No `reqnroll.json` key controls them. `ReqnrollConfiguration`'s public properties are AdditionalStepAssemblies,
  AddNonParallelizableMarkerForTags, AllowDebugGeneratedFiles, AllowRowTests, BindingCulture, ColoredOutput, ConfigSource,
  ConfigSourceText, CustomDependencies, DisableFriendlyTestNames, FeatureLanguage, GeneratorCustomDependencies,
  MinTracedDuration, MissingOrPendingStepsOutcome, ObsoleteBehavior, StepDefinitionSkeletonStyle, StopAtFirstError,
  TraceSuccessfulSteps and TraceTimings (IL, `il-generator-refs.txt:22-40`). The generator DLLs' string literals hold no
  setting for messages (IL, scanned at both UTF-16 alignments). `formatters` and the `REQNROLL_FORMATTERS`,
  `REQNROLL_FORMATTERS_<name>` and `REQNROLL_FORMATTERS_DISABLED` environment variables (literals in `Reqnroll.dll`) steer the
  run-time formatters, not the embedded data.
- The generator drops the messages only when building the pickles fails:
  `WARNING: Failed to process Cucumber Pickles. Support for generating Cucumber Messages will be disabled. Exception: `
  (IL, `UnitTestFeatureGenerator.DeclareFeatureMessagesFactoryMembers`, `il-generator-refs.txt:333`). The changelog has
  "Fix: Formatters: Test execution fails when formatters were disabled due to a generation error (#861)" (3.1.0, `CHANGELOG.md:122`).
- **A stripped resource fails silently** (RAN). `$PROBE/OutlineProbe.Stripped` has the same features, plus a target that
  removes the `EmbeddedResource` after Reqnroll adds it (the `ProbeStripReqnrollMessages` target in `$PROBE/OutlineProbe/OutlineProbe.csproj`).
  The generated code is unchanged, but at run time every feature reads `HasMessages = False` and
  `Source is null; GherkinDocument is null; Pickles count 0`, with no exception (`$PROBE/reflect/reflect-run-stripped.clean.txt:248-249`).
  This matches the IL: the public constructor captures `Assembly.GetCallingAssembly()`, and `ReadEnvelopesFromAssembly`
  returns `Array.Empty<Envelope>()` when `GetManifestResourceStream` gives null (`il-key-types.txt:130-146,183-190`).
- **A host with reflection-based System.Text.Json turned off fails silently too** (RAN). The first run of the reflection app
  printed `HasMessages = False` for every feature. `ReadEnvelopesFromStream` on the real resource stream gave `0 envelopes`

  `PublishTrimmed` or `JsonSerializerIsReflectionEnabledByDefault=false` would lose its pickles the same way (INFERRED).
- A `FeatureInfo` built with the 5- or 6-argument public constructor, as hand-written code or tests do, has
  `FeatureCucumberMessages` null.

So Kronikol cannot rely on the pickle being there, and the plan needs a fallback that builds the name from
`Title` and `Arguments` (section 5).

`ScenarioInfo.Title` is the raw title (every outline in sections 2 and 3). No public member on `ScenarioInfo`, `FeatureInfo`,

## 5. `ScenarioInfo.Title` and `ScenarioInfo.Arguments`

**`Title` is the raw outline title** in every outline looked at: the scratch xUnit v2, xUnit v3, TUnit and no-row-tests builds;
the examples' `Muffins.feature.cs:220`; BreakfastProvider's `StatusTransition.feature.cs:150,193`. All were generated by 3.3.4,
since every outline in git postdates the 3.3.4 pin (`Muffins.feature.cs` first appears at 5ca2bc7c, 2026-05-04). The one 3.3.3
generation in git (ba972c50) holds plain scenarios only, with the same `ScenarioInfo` call shape. For other versions this is INFERRED.

**`Arguments` holds every column, in header order, keyed by the header text, valued with the cell text** (READ in generated code;
IL in the generator):

- `UnitTestMethodGenerator.AddVariableForArguments` emits one `argumentsOfScenario.Add(<header>, <parameter>)` per entry of the
  header-to-parameter mapping, in order (IL, `il-xunit2-generator.txt:812-844`). `CreateParamToIdentifierMapping` builds the mapping
  from the **first** Examples block's header cells, in order (`:1055+`). Every later block must have the same headers in the same
  order or the build fails (case c, case k), so every row's keys are its own header.
- Keys are the header strings as Gherkin parsed them, trimmed and unescaped: `"fruit name"`, `"größe"`, `"case"`, `"class"` (case b).
  Duplicate headers never reach the code (case e).
- Values are the row's decoded cell strings: `""` for an empty cell, `a|b` for `a\|b`, a real line feed for `\n` (case f). They are
  always `string`, because every outline parameter is `string` and every row literal is a string.
- The container is `System.Collections.Specialized.OrderedDictionary`, which enumerates (and lists `Keys` and `Values`) in insertion
  order. `ExamplesBlockResolver.ArgumentValues` already relies on that (`ExamplesBlockResolver.cs:139-146`). A plain scenario gets an
  empty dictionary (case i).

**Rebuilding the pickle name from `Title` and `Arguments` matches Gherkin exactly** (RAN, `$PROBE/reflect/reflect-run-xunit2.clean.txt:250-352`).
For each outline pickle, the reflection app takes the scenario name and the row's header and cell values from the embedded
GherkinDocument, which are the same strings the generated code puts in `Title` and `Arguments`. It applies
`foreach (header, value) name = name.Replace("<" + header + ">", value)` in column order and compares the result with the
pickle's own name. All 13 outline pickles match. That includes the trailing space (`Escaped cells a|b and `), the line feed,
`<missing>` left in place, and `Chained B then B`. A single-pass substitution of the raw title differs on that last one
(`single-pass substitution = "Chained <second> then B" -> DIFFERS`, line 269). A plain scenario has no arguments, so the same
rule gives back its title unchanged, as Gherkin does (`A plain scenario with <x> in its title`).

So a fallback that applies Gherkin's rule to `ScenarioInfo.Title` and `ScenarioInfo.Arguments` gives the same name as the pickle,
with no internals, for every input Reqnroll 3.3.4 accepts (INFERRED for inputs beyond the cases tried; the rule and both inputs
are read from the code).

## Other things the plan should know

- **TUnit and root namespaces.** A project whose root namespace ends in `.TUnit` does not compile: the generated hooks write
  `[global::TUnit.Core.BeforeAttribute(TUnit.Core.HookType.Class)]` without `global::` (`$PROBE/OutlineProbe.TUnit/Features/A_Basket.feature.cs:32`),
  so `TUnit` binds to the project's namespace (`error CS0234`, `$PROBE/build-tunit-rootnamespace-clash.log`). The Kronikol example avoids it
  with `<RootNamespace>Example.Api.Tests.Component.ReqNRollTUnit</RootNamespace>` (`Example.Api.Tests.Component.ReqNRoll.TUnit.csproj:5`).
  This matters for any TUnit test project the plan adds.
- **Pickle numbering.** `pickleIndex` counts every pickle of the feature file in file order: plain scenarios, every outline row
  across all Examples blocks, and rules. It comes in as a literal for a plain scenario (`string pickleIndex = "0";`) and as the
  `__pickleIndex` parameter for a row (sections 2 and 3). `PickleJar.PickleStepSequenceFor` parses it with `Int32.Parse` and throws
  `ArgumentException("Invalid pickle index: ...")` when it is out of range (IL, `il-key-types.txt:368-383`). Kronikol's `FindPickle`
  uses `TryParse` and a bounds check instead.
- **`allowRowTests: false` and `disableFriendlyTestNames: true`** change the test method shape and display name only. `ScenarioInfo`
  is built the same way (section 2).
